# プロトコル・RPC・メッセージング

プロトコル実装、RPCフレームワーク、メッセージブローカー、Webhook、ストリーミング。「内部」は認証ではない。各ホップでピアの識別と、それがどのようにアプリ主体になるかを名指す。スキーマ検証はメッセージ形状を証明するだけで、来歴・資源権限・順序・安全な値を証明しない。ブローカーとアプリの保証は異なる（再試行/順序/受領確認/重複排除/トランザクションを書き出してから状態変更を評価）。パーサ不一致は、二つの具体消費者/スキーマ版/ワイヤ表現＋一つのセキュリティ上重要な解釈差分が必要。

## フレーミング・スキーマ・解釈

- **メッセージ境界と正規化の不一致** — 長さ、圧縮、重複フィールド、未知フィールド、符号化、数値幅、正規化、エンベロープ/本文の優先でコンポーネントが食い違う。生成パーサと手書きパーサ、ゲートウェイ、言語束縛、版変換器を比較。デコード後にどの主体/資源/操作が変わるかを確定。
- **共用体・列挙・既定値の混同** — 未知バリアント、欠落判別子、ゼロ値、既定権限、互換写像が、検証済みケースを想定するコードに達する。網羅的ディスパッチ、既定分岐、新フィールドを解釈する旧消費者を確認。
- **エンベロープとペイロードの識別不一致** — 認可が信頼できる見た目のルーティング/エンベロープメタデータを使い、ハンドラは本文の相反するテナント/アカウント/主体/オブジェクト/送信者に作用する。権威ある情報源を特定し、クライアントが上書きできないことを確認。

## RPCの識別と認可

- **インターセプタとメソッド経路の不整合** — 認証/認可インターセプタが単項メソッドだけに適用され、ストリーム、リフレクション、ヘルス、ゲートウェイ変換経路、互換サービス、個別ストリームメッセージには及ばない。各登録/経路を同一操作と比較。
- **ピア識別とアプリ主体の混同** — mTLS、ワークロード識別、bearerメタデータ、転送識別、ブローカー資格情報がチャネルを認証しても、呼び出し元が制御するフィールドがユーザー/テナントを選ぶ。チャネル識別＋自称主体を決定的ポリシーで束縛。
- **項目ごと・ストリーミングの認可ギャップ** — ストリーム/サブスクリプション/バッチが一度認可され、後の項目が別資源を指定する、または役割/メンバーシップ/トークン失効後も続く。範囲が変わりうる場所で再確認し、サブスクリプションを元の主体に束縛。
- **コールバック・応答相関の混同** — 予測可能/再利用/クロステナントな相関IDが、別の呼び出し元の保留操作を応答/Webhook/取消/受領確認で満たす。各保留要求を認証済みピア・テナント・操作・ライフサイクルに束縛。

## ブローカーとキューの隔離

- **トピック・ルーティングキー・サブスクリプションの範囲ギャップ** — 発行/購読者が別テナントのトピック、ワイルドカード、コンシューマグループ、パーティション、応答キュー、デッドレター経路を選べる。ブローカー強制ACL（見える場合）＋アプリ側の名前空間構築を確認。ペイロード内のテナント文字列は隔離ではない。
- **デッドレター・再試行・診断の開示** — デッドレターキュー/エラートピック/トレース/運用者ビューへ回るメッセージが、秘密やクロステナントのペイロードを低信頼消費者に晒す。失敗経路のポリシー＋墨消しを確認。
- **信頼できない発行者を制御面扱い** — メッセージ本文が自身を管理イベント/プロバイダコールバック/レプリケーション/移行指示と称するが、独立に認証された発行者＋イベント種別がない。署名＋ソース/アカウント/audience束縛を確認してから特権処理。

## 再送・順序・トランザクション

- **重複配送と冪等性ギャップ** — 再試行/再配送が副作用を繰り返す。重複排除がない、変更後に行う、テナント/操作をまたぐキー衝突。ブローカーの配送モデル＋非冪等副作用を確認。
- **順序外・古いメッセージの受容** — 古い状態/失効済みメンバーシップ/取消済み作業/昇格前認可が、新しい状態の後に到着して上書きする。順序/版チェック、トゥームストーン、パーティション変更、復元/再送を確認。
- **受領確認・コミット順序の欠陥** — 永続コミット前に受領確認してセキュリティ上重要な作業を失う、または信頼できない受領確認前にコミットして変更を二重化する。トランザクション送信箱/受信箱＋失敗復旧を評価。
- **部分的な複数消費者遷移** — 複数の消費者が一つの認可/ビジネス遷移を共同実装するが、再試行/部分失敗で部分集合だけコミットされる。原子的に永続すべき不変条件、または現行認可で補償することを特定。

## 全般の手がかり

- メッセージ族ごとに「発行者→ブローカー/転送→ゲートウェイ→消費者→保存」を描き、認証済みピア、権威あるテナント/資源フィールド、検証、副作用を各ホップで記録。
- 同一フィクスチャを全スキーマ版/束縛に与え、重複/欠落/未知/境界/再送/順序外を負荷なしでテスト。
- 通常/再試行/デッドレター/再送/移行/リフレクション/ストリーム/ゲートウェイ変換の経路を比較（セキュリティポリシーは転送変化を生き残る）。

## 確認の要点

- 現実的な発行者/ピア、受け入れられるメッセージ、認証済みチャネル識別、影響を受ける主体/資源、不正変更/開示を名指す。
- 不一致は両パーサ/消費者＋解釈差分の値を引用（どちらかが安全に拒否すれば確定しない）。
- 再送/順序は実際の配送保証を確定し、有界なローカル/メモリ内転送で不変条件破れを再現。
- 認可/隔離は全インターセプタ/ブローカーACL/ゲートウェイ/消費者層をソースで検証。外部付与は要検証。
- confirmed は完全なメッセージライフサイクル＋観測された意味ある結果がある時のみ。要検証はブローカー/識別/経路/配送の事実を具体的に。
