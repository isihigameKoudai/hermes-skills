# 検知・対応（Anthropic）

Anthropic `.claude/skills/dnr-hunt` と `dnr-respond` から改作。脆弱性ワークフローの侵害後版 — 攻撃者は**既にログの中にいる**。見つけ、被害範囲を見積もり、対応を（実行せずに）提案する。

流れ: **dnr-hunt**（見つける）→ **dnr-respond**（範囲＋計画）→ **トリアージ**（欠陥を検証）→ **修正**（直す）。

## 共通の厳格ルール（このトラックの契約）

1. **ログ証拠だけでは脆弱性を確定しない。** `confirmed_exploited` は3つ全てが必要: ログ証拠＋ソースで特定した欠陥（ファイル＋関数）＋このセッションでローカルインスタンスに発射したPoC。`suspected`＝ログ証拠はあるがPoC未発射。`attempted_not_vulnerable`＝攻撃トラフィックは観測されたが、ソースが防御を示しPoCが跳ね返る。
2. **読まずに問い合わせる。** ログファイルを `cat` しない。`wc`/`du`/`head`/`tail` で概観し、`grep`/`rg`/`awk`/`sort`/`uniq` のパイプライン（または状態を扱う `python3`）で問い合わせる。小さなアラートキュー/エラーログは全体を読んでよい。
3. **提案はしても実行しない。** ブロック/無効化/ローテーション/設定変更はどの環境でもしない。
4. **ローカルのみ。** PoCは自分で起動したインスタンスに対して `127.0.0.1` で発射。遠隔ホストには触れない。
5. **全ての数値は問い合わせの結果。** 行数、要求数、時間幅、影響顧客数 — それぞれ今セッションのパイプライン実行から取り、台帳に引用。推定しない。

## dnr-hunt — 能動的脅威ハント（アラート無し）

問い: 「ここに、あってはならないものがあるか？」まずベースラインを取り、それから仮説→問い合わせ→ピボット。全段階を文書化し、全容疑をソース確認と実演（デトネーション）で裏付けてから「本物」と呼ぶ。

- **段階0 — 入力の特定/検証:** ログディレクトリとアプリソースを解決。ファイルを棚卸し（`du -h`, `wc -l`, `head -2`, `tail -2`、形式とawkフィールド位置を特定）。
- **段階1 — コーパスの概観（仮説の前にベースライン）:** 時間窓＋要求/日、ステータスヒストグラム、上位トーカー（IPあたり要求の上位20対中央値）、上位ルート（idを正規化 `/orders/123`→`/orders/N`）、ユーザーエージェントの棚卸し（自動化UAをフラグ: curl、python-requests、sqlmap、Go-http-client、zgrab）、認証の様相（どのフィールドがユーザーを運ぶか、複数IPからのアカウント、失敗ログイン源）、ルート別サイズプロファイル（最小/中央/最大—通常小さいルートでの大きな外れ値はデータ持ち出しの兆候）、エラーログをタイムスタンプでアクセスログに対応付け、アラートキュー（規則/ソース/対象/重大度—アラートは*入力*であって所見ではない。アラートの騒音も沈黙も情報）。各観察を正確なパイプラインとともに記録。
- **段階2 — ハントループ（仮説台帳が必須）。** 仮説のない問い合わせ、台帳行のない仮説はしない。列: `# | 仮説 | 問い合わせ | 結果 | 判定 | 次のピボット`。判定: `supported`/`refuted`/`needs-pivot`。**初回スイープ:** (1) サーバーエラー—誰がどのルートで5xxを起こし、どんなペイロードか（攻撃者入力を引用するアプリエラーは探査の痕跡）; (2) 判定済みの全アラート—フラグされた活動は成功したか; (3) 上位トーカーの外れ値; (4) クエリ文字列の注入文法（`%27`、`UNION`/`SELECT`、`--`/`%23`、`AND 1=1`/`AND 1=2`）—IPごとにデコードして列を再構成; (5) 列挙パターン（機械的なペースでの連番オブジェクトIDアクセス）; (6) 認証異常（アカウントの新IP、失敗→成功、1IPが1アカウントとして異常量）; (7) サイズ異常（ルート中央値の倍数の応答）; (8) 静かな時間帯（低速な長期キャンペーンは午前3時に際立つ）。**両方向にピボット**（どうやってここに来たか、次にどこへ行ったか）。**停止条件:** 2連続ラウンドで新しいエンティティが出ない。
- **段階3 — ソース確認:** ルートを示唆する各容疑についてハンドラを読み、脆弱なら欠陥を正確に名指し（ファイル、関数、行）。脆弱でなければ防御を同じ精度で名指す（トラフィックを `attempted_not_vulnerable` に変える。必ず記録）。兄弟ルートに同じ欠陥クラスがないか確認。
- **段階4 — PoC実演（`confirmed_exploited` のゲート）:** アプリをローカルでシード＋起動（バックグラウンド、`/healthz` をポーリング）。**最小**PoCを発射し、判定で非脆弱とされたルートに**陰性**PoCを発射。`kill <pid>`。アプリが起動できないなら verdict は `suspected` のまま。
- **段階5 — 出力:** `INCIDENTS.json`＋`INCIDENT_REPORT.md`（要約≤3文、統合タイムライン、インシデントごとの証拠＋ソース確認＋PoC記録＋影響、「除外」節、完全な仮説台帳を付録に）。

## dnr-respond — 手掛かりありのインシデント対応

順に答える: **何が起きたか、成功したか、どこまで広がったか、どう対処するか。** 手掛かりは `INC-n` id、貼り付けられたアラート、IOC（IP/アカウント/ルート/セッション）、自由文。

- **段階1 — 範囲:** 各エンティティが触れたものを全て引き出す（IPごとに全要求を時系列で、アカウントごとに全ログイン＋認証済み要求を履歴パターンと対比、ルートごとに同じ方法で誰が他にヒットしたか）。リングを一度拡張。エラーログ＋アラートキューを1つのタイムラインに対応付け。
- **段階2 — verdictと被害範囲:** ステータスコードだけでは答えにならない — 401の壁＝否。異常サイズ・エラー→成功・データ形状の200＝是。定量化: どのルート/テーブル、何レコード、どの期間、何人の別ユーザー/顧客（全数値はパイプラインから）。封じ込め状況: 継続中か停止済みか。
- **段階3 — 根本原因とPoC:** ハントと同じ基準（ファイル/関数精度で欠陥/防御を名指し、兄弟、最小PoC＋陰性PoC）。実行可能なアプリが無ければ上限 `suspected`。
- **段階4 — 対応計画（提案のみ、実行しない）**＋`RESPONSE.md`。各行動に what／why／間違った場合のリスクを付す:
  1. verdictと要約（3文）。2. タイムライン。3. **封じ込め**（ブロック/停止/レート制限＋間違えたら何が壊れるか。例: NATのIPを塞ぐと正規ユーザーを閉め出す）。4. **根絶と修復**（ファイル/関数レベルのコード修正をトリアージ互換の脆弱性エントリとして引き渡し）。5. **復旧**（どの資格情報を正確にローテーションするか、どの顧客に通知するか、攻撃者が退去したことを確認する監視）。6. **検知エンジニアリング**（もっと早く捉えられたであろう規則: ルート別ソースのエラーレート、連番IDのペース、量を伴う新IPアカウント。どのアラートが発火し、どれが騒音だったか）。7. 未解決の問い。

## INCIDENTS.json スキーマ

`target`; `incidents[]` — 各 `{id (INC-n), title, verdict (confirmed_exploited|suspected), attacker_ips[], accounts_involved[], vuln{type, route, file, function}, timeline[{ts, event}], impact, evidence["<log file>: <pipeline> → <result>"], poc{command, verified}}`。`ruled_out[]` — `{subject, verdict (attempted_not_vulnerable|benign), reason}`。ルーティング規則: `incidents`＝起きたこと/起きたかもしれないこと。`attempted_not_vulnerable`/`benign` は `ruled_out` へ、決して `incidents` へ入れない。

## デモ（dnrcanary）— 植え付けられたキャンペーンが教えること

意図的に脆弱な Flask＋SQLite の店舗と、植え付けられたキャンペーン・良性トラフィック・騒がしい行き止まりを含む1週間分の生成ログ。回答キー（`ground_truth.yaml`）がハンターの見つけるべきものを符号化する:

1. **`sqli_search`** — `/search` の f-string SQL注入（`WHERE name LIKE '%{q}%'`）。3段階: 偵察（良性に紛れる）、探査（9要求中4件が500→sqliteエラーが列数を漏らす）、持ち出し（`sqlite_master` でスキーマ発見、その後UNION SELECT 20ページ。応答約3.4KB対良性≤2.1KB）。`users` テーブル（500行: username, email, password_hash）を窃取。
2. **`idor_orders`** — `/orders/<id>` のIDOR（ログインは必須だが所有権を確認しない）。`GET /orders/1..240` を約10秒間隔で240件、全て200。240注文／193顧客を露出。
3. **陽動 `scanner_login`** — `/login` へのsqlmapバースト（622要求）。正しくパラメタ化されている→全て401、アプリエラーゼロ→verdict `attempted_not_vulnerable`。

2つのインシデントは**連鎖する**: 窃取された `password_hash`（弱い `password123`、無saltのsha256）をオフラインで割り、約26時間後に別IPから注文ウォークに再利用。教訓: WAFシグネチャはデコード済みフォーム本文にのみ一致し（URLエンコードされたクエリ文字列は警告されず）、IDORは**アラートもエラーログ項目も生まない**—アクセスログのパターン（1セッション、連番id、安定したペース、単一IP）としてのみ見える。
